# 🌱 Career Quest — команда Flower Power

HackAlem AI · трек Halyk Bank · кейс **Career Quest**.

Веб-приложение подбирает сотруднику **1–3 добровольные активности развития** и объясняет каждую минимум тремя
факторами: грейд и цель, разрывы в навыках, история участия, требования следующего уровня. Если отметить активность
пройденной, уровни навыков, прогресс к цели и рекомендации пересчитываются. **AI-коуч** превращает желание
сотрудника, написанное своими словами, в карьерную цель из справочника ролей. HR видит, какие навыки отстают чаще
всего, у кого нет следующего шага и как сотрудники участвуют в активностях.

## Быстрый старт

Нужен [uv](https://docs.astral.sh/uv/) (Python 3.12 он поставит сам) **или** Docker.

```bash
# Вариант 1: Docker
docker compose up --build                          # http://localhost:8501

# Вариант 2: локально
uv sync
uv run uvicorn career_quest.api:app --port 8501    # http://localhost:8501
```

Без настроек приложение работает офлайн в демо-режиме: на экране входа выбирается роль «Я сотрудник» или «Я HR»,
пароль не нужен. Настройки задаются в `.env` (шаблон — `.env.example`, файл `.env` в Git не попадает):

| Переменная | Зачем |
|---|---|
| `OPENAI_API_KEY` | Включает AI-коуча и AI-объяснения. Пусто — коуч работает по ключевым словам, объяснения строятся из рассчитанных факторов |
| `OPENAI_MODEL` | Модель, по умолчанию `gpt-4.1-mini` |
| `CQ_EMPLOYEE_ID`, `CQ_EMPLOYEE_PASSWORD`, `CQ_HR_PASSWORD` | Включают вход по паролю: сотрудник видит только свой профиль. Задаются все три вместе |
| `CQ_DATA_DIR` | Другой каталог с данными (по умолчанию `data/`) |
| `CQ_PORT` | Порт для Docker (по умолчанию 8501) |

Docker читает `.env` сам. Локально: `uv run --env-file .env uvicorn career_quest.api:app --port 8501`.

Документация API (Swagger): http://localhost:8501/api/docs.

## Демо-сценарий (5–7 минут)

1. **Вход сотрудника.** «Я сотрудник» → «Войти». Шапка показывает путь к цели: кольцо прогресса (покрытие
   требуемых уровней навыков), число обязательных навыков ниже цели, рост уровней после последней оценки и личные
   достижения.
2. **AI-коуч.** Напишите «хочу через год стать тимлидом в аналитике» → «Подобрать» → «Сделать целью и пересчитать
   шаги». Цель, прогресс и рекомендации сразу меняются. Коуч понимает русский, казахский и английский.
3. **Рекомендации.** У каждой карточки: «+N% к цели», формат, часы, дата старта, какие навыки вырастут, и список
   факторов со знаком «+» или «−» и числами, например «Лидерство: 2 → 3, для цели нужно 4 (обязательный навык)».
   Кнопка «Объяснить с AI» формулирует те же факторы связным текстом на выбранном языке (ru/kk/en).
4. **Прогресс.** «Отметить как пройдено» → уровни навыков растут, кольцо и квест обновляются, следующие шаги
   пересчитываются. За новое достижение — конфетти.
5. **Проверочные профили.** Выйдите и войдите как «Я HR» → «Данные» → загрузите `demo/trap_employees.json` и
   `demo/trap_history.csv`. В списке сотрудников появятся три профиля `TRAP_1…3`, на которых правило
   «качать самый слабый навык» ошибается:

   | Профиль | Самый слабый навык | Почему он не первый | Что рекомендуем |
   |---|---|---|---|
   | `TRAP_1` | Public Speaking = 0 | три пропуска таких активностей, а System Design критичен для Senior | EV_006, System Design |
   | `TRAP_2` | Cloud = 0 | цель — Data Analyst Senior, для неё критичны A/B-тесты и статистика | EV_021, A/B + статистика |
   | `TRAP_3` | Public Speaking = 0 в оценке | после оценки два занятия клуба подняли навык до требования | EV_006, System Design |

   Файлы жюри в том же формате загружаются через ту же форму.
6. **HR-обзор.** «Обзор HR»: какие навыки отстают чаще всего, список «нет подходящего следующего шага», участие и
   доля завершений по каждой активности. Рейтингов сотрудников нет. В профиле сотрудника HR видит нейтральный текст
   и не может менять цель — её выбирает сам сотрудник.

## Как устроена рекомендация

Логика — в `career_quest/scoring.py`, детерминированная и полностью покрытая тестами.

1. **Текущие навыки** — уровни из последней оценки плюс приросты активностей, завершённых после неё
   (с учётом `max_level`, в порядке дат). Без этого рекомендации строились бы по устаревшим данным.
2. **Цель** — `career_goal`, если задана (в том числе в другой роли), иначе следующий грейд своей роли. Для Lead без
   цели — текущий профиль.
3. **Кандидаты** — только добровольные события для роли и грейда сотрудника или цели, с выполненными пререквизитами,
   с сессией в будущем или в своём темпе. Пройденные события не повторяются (кроме клуба `EV_036`), начатые тоже.
4. **Оценка** — взвешенная сумма факторов (веса собраны в `WEIGHTS` в начале модуля):

   | Фактор | Вес | Смысл |
   |---|---|---|
   | `critical_gap` | +3.0 за уровень | закрывает критичный навык цели — главный фактор повышения |
   | `required_gap` | +1.5 за уровень | закрывает другой требуемый навык цели |
   | `target_alignment` | +1.0 | событие рассчитано на целевую роль и грейд |
   | `grade_fit` | +0.5 | событие для текущего грейда, база для следующего |
   | `goal_alignment` | +0.5 | служит явной карьерной цели сотрудника |
   | `history_avoidance` | −1.0 / −0.5 за запись | пропуски, отказы, брошенные активности по тем же навыкам / того же типа |
   | `engagement` | +0.5 за завершение (до 2), +0.25 | завершал похожие активности, в том числе по своей инициативе |
   | `feedback` | ±0.5 | средняя оценка похожих активностей ≥ 4 или ≤ 2 |
   | `availability` | +0.5 | в своём темпе или сессия в ближайшие 14 дней |
   | `duration` | −0.05 за час сверх 8 | длинные программы чуть ниже |

5. **Фильтр показа.** Рекомендация показывается, только если закрывает хотя бы один разрыв к цели, её сумма
   положительная и у неё не меньше трёх ненулевых факторов. Если подходящего события нет, сотрудник попадает в
   HR-список «нет следующего шага»: система не выдумывает шаг.
6. **Завершение** (`complete_activity`) добавляет запись `completed` на дату среза. Повторная отметка того же
   события в тот же день отклоняется, клуб `EV_036` можно отмечать в разные дни.

## Роль AI

Выбор и ранжирование активностей делает прозрачная формула выше: её можно проверить по цифрам. AI работает там,
где нужен язык, и никогда не выдумывает факты:

- **AI-коуч** (`career_quest/coach.py`). Превращает свободный текст («хочу через год стать тимлидом в аналитике»)
  в цель — роль и грейд. Модель может выбрать только значения из справочника ролей: это задано строгой JSON-схемой
  с перечислением допустимых ролей и повторно проверяется в коде. Просьбы не по теме («хочу в отпуск») и попытки
  подменить инструкции дают «цель не найдена». В модель уходят только текст и текущая роль, без имени и истории.
  Без ключа или при ошибке цель подбирается по ключевым словам на ru/kk/en.
- **AI-объяснение** (`career_quest/explain.py`). Превращает рассчитанные факторы в короткий текст на языке
  сотрудника (ru/kk/en). Ответ проверяется: каждое утверждение ссылается на свой фактор и сохраняет его числа.
  При ошибке, тайм-ауте (8 с) или без ключа показываются те же факторы без LLM.

Оба вызова — OpenAI Responses API с `store: false`.

## Геймификация без давления

Всё личное, без рейтингов и сравнения с коллегами (так требует кейс):

- **Кольцо прогресса к цели** — доля требуемых уровней навыков, которые уже достигнуты. Это не вероятность повышения.
- **«+N% к цели»** на каждой рекомендации — насколько вырастет кольцо после этого шага.
- **Квест** — навыки, которые ещё ниже уровня цели, обязательные отмечены золотой полосой.
- **7 личных достижений** (`career_quest/quest.py`): первый шаг, по своей инициативе, возвращение к навыку после
  пропуска, рост после оценки, ключевой навык закрыт, полпути, готов к цели. Новое достижение — конфетти.
- **Навыки по уровню:** 🌱 начальный (0–1), 🌿 средний (2–3), 🌸 высокий (4–5); ✓ — навык уже на уровне цели.

Серий «не пропусти день», штрафов и механик вокруг обязательного обучения нет.

## Архитектура

```
career_quest/api.py          FastAPI: JSON API, сессии, роли, раздача веб-клиента
web/                         веб-клиент: index.html, styles.css, app.js (без сборки и фреймворков)
career_quest/scoring.py      текущие навыки, цель, кандидаты, факторы, рекомендации, завершение
career_quest/quest.py        квест к цели, прогресс, личные достижения
career_quest/coach.py        AI-коуч: цель из свободного текста + офлайн-разбор
career_quest/explain.py      AI-объяснение рекомендаций + офлайн-фолбэк
career_quest/factor_text.py  русский текст факторов для интерфейса
career_quest/labels.py       русские названия ролей, навыков, активностей, статусов
career_quest/access.py       роли сотрудник/HR, демо-режим
career_quest/snapshot.py     импорт доп. профилей / полного набора, экспорт снимка (ZIP)
career_quest/models.py       Pydantic-модели формата датасета
career_quest/data.py         загрузка, валидация ссылок, слияние доп. профилей и истории
app.py                       запасной интерфейс на Streamlit: uv run streamlit run app.py
data/                        датасет организаторов (описание в data/README.md)
demo/                        три проверочных профиля-ловушки
tests/                       pytest: данные, скоринг и ловушки, квест, коуч, объяснения, доступ, API, UI
```

Каждая сессия браузера получает на сервере свою копию данных: отметки о прохождении и смена цели не видны другим
сессиям и переживают перезагрузку страницы. Доступ проверяется на сервере: сотрудник открывает только свой
профиль, HR-отчёты и загрузка данных доступны только HR, цель меняет только сам сотрудник.

«Сегодня» для системы — дата среза датасета **2026-10-01**, а не системные часы.

## Применимость и развитие

### Почему это не только про банк

Движок не привязан к конкретной компании: ему нужны четыре файла в формате датасета — матрица навыков по ролям
и грейдам, каталог активностей, профили и история участия. Логика не меняется: данные достаточно привести к этому
формату. Шкала грейдов (Junior → Middle → Senior → Lead) и типы активностей пока заданы в коде — их вынос в
настройки входит в следующие шаги.

Пример — государственная служба. Для всех входных данных модели там есть прямые аналоги:

| Career Quest | Госслужба |
|---|---|
| `role_profiles` (требования по грейдам, критичные навыки) | квалификационные требования к должностям и категориям |
| `events` (добровольные активности; обязательные учитываются в истории, но не рекомендуются) | добровольное обучение; обязательное повышение квалификации — только в истории |
| `activity_history` (пропуски, отказы, завершения) | учёт прохождения обучения в кадровой системе |

Та же логика «разрыв до требований → объяснимый шаг» помогает госслужащему видеть, зачем ему конкретная
программа, а кадровой службе — где системно проседают компетенции.

### Что даёт организации

- Сотрудник получает не список дедлайнов, а 1–3 шага с понятной причиной и видимым прогрессом.
- Бюджет на развитие идёт в активности, которые закрывают реальные разрывы к следующему грейду.
- HR видит проседающие навыки и людей без следующего шага до того, как они выпадут из развития.

### Следующие шаги

1. **Веса на реальных исходах.** Сейчас веса заданы вручную. С данными о том, что после активности навык вырос
   на оценке или человек получил повышение, веса можно подобрать по данным, сохранив факторы объяснимыми.
2. **Внутренняя мобильность.** Считать покрытие требований не только для цели, а для всех ролей и показывать,
   к какой соседней роли сотрудник уже близок.
3. **Настраиваемая модель данных.** Вынести шкалу грейдов, типы активностей и повторяемые события в настройки,
   чтобы подключать организации со своей структурой должностей.
4. **Локальная LLM.** Для контуров, где данные не могут покидать организацию: вынести адрес модели в настройку
   и работать с локальной моделью. В модель и сейчас уходят только факторы или текст желания, а без неё всё
   работает офлайн.
5. **Интеграции.** Сессии в календарь, напоминания в мессенджер — только по согласию сотрудника, без давления.
6. **Промышленная инфраструктура.** Корпоративный вход (SSO) и хранение прогресса в базе данных.
7. **Локализация.** Язык сотрудника уже есть в данных (`preferred_language`), AI-коуч и объяснения работают на
   ru/kk/en. Дальше — перевести интерфейс на казахский и английский.

## Ограничения

- **Прогресс хранится в памяти сервера.** Он переживает перезагрузку страницы, но сбрасывается при перезапуске
  сервера. Чтобы сохранить результат, скачайте ZIP-снимок на странице «Данные» и загрузите его обратно через
  «Заменить весь набор данных».
- **Вход упрощённый.** Пароль сотрудника привязан к одному `CQ_EMPLOYEE_ID`, это демонстрация разделения ролей,
  а не корпоративная аутентификация. Без переменных включается явно помеченный демо-режим, где можно открыть
  любой профиль.
- **Каталог ограничен.** Если все подходящие события пройдены или закрыты пререквизитами, рекомендаций нет. Такие
  сотрудники видны HR.
- **Веса подобраны вручную** под логику кейса и проверены на ловушках, а не обучены на данных: в датасете нет
  меток «рекомендация была полезной».
- **Строгая проверка AI-объяснений** иногда отклоняет ответ модели, если в нём изменилось хоть одно число. Тогда
  показываются рассчитанные факторы — факты не теряются.
- **GitHub CI** сейчас не запускается из-за ограничений биллинга аккаунта. Локально все проверки проходят.
- Данные синтетические, реальных людей нет.
